# 内容中台导入接口说明（给研发）

更新日期：2026-11-24
状态：提议，待研发评审。接口还不存在，插件已按这份说明写好，可以按评审结果调整。

依据：

- 数据按《导入数据标准》（`schema_version` 1）来，它对应《需求文档》里的对象模型。这两份由产品另行提供。
- 只读阅读了 `kabo-sh/kabo` 在 2026-11-24 的主干（`917ac75`），没有改动仓库。

## 1. 先说最重要的：标准和线上不一致

插件提交的数据是按需求文档的模型来的，线上内容中台现在存不下其中大部分。所以这次需要研发做的不只是「开一个入口」，还包括「让后端能存这些字段」。

| 标准里的数据 | 线上现在（`content-assets-preview.ts`） |
|---|---|
| 工作流：名称、描述、工具类型、更新说明、输入要求、**步骤列表**、预估成本、文件清单、来源 | 工作流记录只有标题和一个 zip |
| 成片：所用工作流和版本、关联的爆款、用到的素材、发布链接 | 成片记录是一张制作信息表（制作指令、创作要求、提示词、工具、模型、参数等），可关联一条**已发布**的工作流 |
| 素材：名称、素材组、适用账号 | 素材只有标题和「用途」（Input / Output / 待确认） |
| 爆款：链接，其余由平台抓取 | 爆款只存了一条链接，没有抓取 |
| 所属 Project、账号池、素材组由平台管理 | Project 写死三个，没有账号池和素材组 |
| 批次、导入任务 | 没有 |

两种推进方式，需要研发和产品一起定：

- **A. 后端按需求文档的模型做。** 插件和标准都不用再改。工作量大，对应需求文档 P0 的范围。
- **B. 过渡期先映射到线上现有字段。** 见第 6 节的对应表。能尽快用起来，但步骤会被压成一段文字，素材组、适用账号、发布链接、工作流的结构化信息会丢。等后端模型做好后再切回 A。

无论哪种，工作流包里都带着一份完整的 `manifest.json`（标准第 3 节的全部字段）。即使线上只把它当 zip 存，信息也没有丢，之后可以从包里重新解析出来。

## 2. 为什么需要新入口

| 现状 | 位置 | 对插件的影响 |
|---|---|---|
| `/v1/admin/content-assets-preview` 要求管理员的浏览器会话，并校验同源 | `apps/api/src/admin/routes.ts:154-173` | 从 Claude、Codex 里发请求会被拒 |
| MCP 的登录令牌不能带管理员权限 | ADR-0077，`docs/privacy-security.md` | 不能简单地加一个管理员专用的 MCP 工具 |
| MCP 请求体上限 256 KiB | `apps/web/src/proxy.ts` | 文件不能放在 MCP 工具参数里 |

提议：**不走 MCP，新开一组只认「导入令牌」的 HTTP 接口。**

## 3. 导入令牌

| 项 | 提议 |
|---|---|
| 谁能生成 | 管理员本人，在内容中台页面上，用现有的管理会话 |
| 能做什么 | 只能在生成者本人名下**新建草稿**，读第 4.1 节的上下文，以及查看自己发起的导入任务 |
| 不能做什么 | 不能读别人的记录、不能读文件、不能发布、不能编辑、不能删除 |
| 形态 | 随机串，带可识别前缀（如 `kca_`），明文只在生成时显示一次，服务端只存哈希 |
| 有效期 | 建议 90 天，可随时撤销 |
| 每次使用时 | 重新确认生成者仍然是管理员。现有的 `isAdmin(userId, sessionId)` 需要会话，这里需要一个只按用户查的版本 |
| 页面上展示 | 名称、创建时间、最近使用时间、撤销按钮 |

它不是产品或 MCP 的 bearer token 附带出来的权限，而是管理员在后台显式生成的、范围只有「给自己建草稿」的凭据。它仍然是一种新的管理能力，需要补一份 ADR（或修订 0077），并更新 `docs/privacy-security.md`。

## 4. 接口

前缀暂定 `/v1/content-assets-import`，认证 `Authorization: Bearer <导入令牌>`。流程是三步：登记批次、直传文件、确认。文件不经过这组接口，所以没有请求体大小的问题。

### 4.1 读上下文

`GET /v1/content-assets-import/context`

```json
{
  "user": { "name": "陈晓" },
  "projects": ["Kabo", "Decormake"],
  "accounts": [{ "id": "…", "handle": "@kabo.sample", "platform": "TikTok", "project": "Kabo" }],
  "asset_groups": ["叠字短片", "混剪模板"],
  "workflows": [{ "workflow_id": "…", "name": "叠字短片工作流", "project": "Kabo", "versions": ["v3", "v2", "v1"] }]
}
```

### 4.2 登记批次

`POST /v1/content-assets-import/batches`，JSON。请求体就是标准第 2 节的批次清单，加上每个文件的登记信息：

```json
{
  "schema_version": 1,
  "client": "claude-plugin",
  "client_version": "0.2.0",
  "project": "Kabo",
  "accounts": [],
  "title": "叠字短片 · 首次导入",
  "idempotency_key": "…",
  "workflows": [{
    "key": "overlay-text",
    "name": "…", "description": "…", "tool": "claude", "project": "Kabo", "change_note": "…",
    "related_virals": ["…"], "inputs": { "materials": [], "secrets": [] },
    "steps": [], "cost": {}, "entry": "SKILL.md", "secrets_removed": 2, "origin": null,
    "secrets_checked": true,
    "file": { "ref": "overlay-text", "name": "overlay-text.zip", "size": 63233, "sha256": "…" }
  }],
  "outputs": [{
    "key": "out-1", "name": "", "workflow": "overlay-text", "viral": "https://…",
    "assets": ["night-city"], "publish_links": [], "project": "Kabo",
    "file": { "ref": "out-1", "name": "final.mp4", "size": 26535270, "sha256": "…" }
  }],
  "assets": [{
    "key": "night-city", "name": "示例夜景 01", "groups": ["叠字短片"], "project": "Kabo", "accounts": [],
    "file": { "ref": "night-city", "name": "night-city.mp4", "size": 19293798, "sha256": "…" }
  }],
  "virals": [{ "url": "https://…", "project": "Kabo", "accounts": [], "method": "" }]
}
```

说明：

- `workflows[]` 里的字段和工作流包里的 `manifest.json` 相同，只是不带 `files` 清单（清单在包里）。
- `outputs[].workflow` 是这一批里的 `key`，或者 `{ "workflow_id": "…", "version": "v3" }` 指向平台上已有的版本。
- `secrets_checked` 表示用户在对话里确认过这个工作流的密钥已核对。插件只会提交为 `true` 的工作流。
- `idempotency_key` 由整份清单的内容算出。同一个令牌下重复提交相同的 key，返回第一次的结果。

返回：

```json
{
  "job_id": "…",
  "url": "https://kabo.sh/admin/content-assets?job=…",
  "uploads": [
    { "ref": "overlay-text", "method": "PUT", "url": "https://storage.googleapis.com/…", "headers": {} }
  ]
}
```

`uploads` 是每个文件的直传地址。插件按给定的方法和请求头把文件发过去，**不会**把导入令牌带到这些地址上。可以沿用 `upload_file` 的 V4 签名可续传地址的做法；那条现成的路径白名单不含 zip、文件落在用户个人空间，所以这里需要单独一条。

这一步就应该做完第 5 节的校验，不通过的直接返回 400 和原因，不发上传地址。

### 4.3 确认

`POST /v1/content-assets-import/batches/{job_id}/complete`

服务端核对每个文件的大小和哈希，再做一遍密钥扫描，然后建草稿。返回每一项的结果：

```json
{
  "url": "https://kabo.sh/admin/content-assets?job=…",
  "items": [
    { "type": "工作流", "key": "overlay-text", "name": "叠字短片工作流", "status": "已存为草稿", "draft_url": "https://…" },
    { "type": "爆款", "name": "https://…", "status": "已存在", "message": "库里已有这条爆款" },
    { "type": "成片", "key": "out-1", "name": "…", "status": "失败", "message": "视频无法转码" }
  ]
}
```

`status` 只有三种：`已存为草稿`、`已存在`、`失败`。插件把 `message` 原样转述给用户。

### 4.4 错误

统一返回 `{ "message": "给用户看的中文原因" }`。

| 状态码 | 情况 |
|---|---|
| 400 | 清单不合法。`message` 写清是哪一项的哪个字段 |
| 401 | 令牌无效、过期或已撤销 |
| 403 | 生成令牌的人不再是管理员 |
| 409 | `schema_version` 不支持，提示升级插件 |
| 503 | 暂时失败，可重试 |

## 5. 服务端校验

和标准第 8 节一致。插件在本机已经做了同样的检查，目的是尽早报错；服务端仍然要自己做。

| 校验 | 不通过时 |
|---|---|
| 「必须」的字段是否都有 | 该项失败，说明缺什么 |
| 步骤的 `type` 是否在五种之内；`prompt` 和 `模型生成` 是否有 `content` 和 `model` | 该项失败 |
| 步骤引用的文件是否在包里 | 该项失败 |
| 成片的 `workflow`、`assets` 引用是否存在 | 该项失败 |
| 链接是否属于 TikTok、Instagram、YouTube | 该项失败 |
| 爆款链接是否已存在 | 不新建，返回「已存在」 |
| 包里是否还有密钥的值 | 不拒绝。自动剔除，并在草稿里提示又剔除了几处 |
| Project、账号是否存在 | 该项失败。素材组不存在则新建 |
| 「应该」的字段缺失 | 不算失败，记进草稿的「需要核对的事项」 |

## 6. 过渡期：映射到线上现有字段（方案 B）

如果先不改后端的数据模型，可以在新接口内部把标准的数据转成现有记录。信息会有损失，下表标了丢什么。

| 标准 | 线上现有记录 | 丢什么 |
|---|---|---|
| 工作流 | `kind: 工作流` 的记录，zip 作为文件，`name` → 标题，`secrets_checked` → `checked` | 页面上看不到步骤、输入要求、成本、描述；它们只在 zip 里的 `manifest.json` 中 |
| 成片 | 成片记录：`file` → 成片视频；工作流的 `steps` 拼成文字 → 「制作指令 / 脚本」；步骤里的模型 → 「模型」；工作流 `related_virals` 或成片的 `viral` → 「参考链接与说明」；用到的素材 → 素材文件 | 关联爆款变成一段文字，不是真正的关联；发布链接没有地方放；多条成片共用一个工作流草稿时关联不上（现在只能关联已发布的工作流） |
| 素材 | `kind: 素材` 的记录，`name` → 标题 | 素材组、适用账号没有地方放 |
| 爆款 | `kind: 爆款视频` 的记录，`url` | 不抓取，没有标题和数据；`method` 没有地方放 |
| 批次和导入任务 | 没有对应 | 看不到进度和失败项，只能在确认接口的返回里看 |

## 7. 需要研发定的事

| # | 问题 | 说明 |
|---|---|---|
| 1 | 方案 A 还是 B | 见第 1 节。这决定工作量和排期 |
| 2 | 这个方案和 ADR-0077 是否冲突 | 是否需要新 ADR、更新隐私安全文档、登记 `NON_PRODUCT_ROUTE_EXEMPTIONS` |
| 3 | 直传地址怎么发 | 是否沿用 V4 签名可续传地址；zip 和音频的白名单；大小上限（产品的要求是不设上限） |
| 4 | 令牌有效期和数量上限 | 提议 90 天，每人最多 5 个 |
| 5 | 文字字段的长度上限 | 真实对话试跑时，单个步骤的提示词可以有几千字。需要明确上限，插件好在本机提前提示 |
| 6 | 草稿的「需要核对的事项」 | 标准里「应该」的字段缺失时要在草稿上提示。线上草稿现在没有这个位置 |
| 7 | 日志 | 按现有规则，不记文件名、标题、步骤内容、令牌；操作者只记哈希 |
| 8 | 正式环境 | 我没能确认内容中台是否已经部署到正式环境。插件默认连 `https://kabo.sh`，可以用环境变量 `KABO_CONTENT_ASSETS_URL` 指到预发 |
| 9 | 拉取工作流到本地 | 标准第 3.6 节：拉取时平台往 `manifest.json` 里写 `origin`，再次导入时据此判断是新版本还是复制。插件还没做拉取，需要一个下载工作流包的接口 |

## 8. 插件这边已经做的

- 按标准生成批次清单和工作流包。工作流包里的 `manifest.json` 包含标准第 3 节的全部字段，文件清单带大小和哈希。
- 本机校验：第 5 节里不依赖平台数据的那些。
- 工作流打包时剔除密钥的值，`.env` 文件不打包，密钥名称记进 `inputs.secrets`。每处剔除都列出文件和行号给用户核对。
- 没有用户的密钥核对确认时，不提交那个工作流，也不提交依赖它的成片。
- 导入令牌由用户自己存到本机文件或环境变量，插件和 agent 都不读取、不打印它，也不会把它发到直传地址。
- 已对着本地模拟的服务跑通三步流程。真实接口没有，所以没有真实联调过。
